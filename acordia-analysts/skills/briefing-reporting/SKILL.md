# Briefing & Written Reporting

## Objective

Communicate the operational picture and the recommended course of action crisply, so the recipient can decide and act without reconstructing your analysis or misreading your confidence.

## When to use

- Handing off a judgement, a target read, or a recommended move to a decision-maker or the next operator.
- Producing a written product (spot report, target package, after-action) others will act on.

## Method

- Lead with the bottom line: the judgement and the recommended action, before any supporting detail.
- Separate fact from inference from recommendation, and mark the confidence on each (see calibrated-confidence).
- Give only the evidence that changes the decision; push the rest to an annex, and name the key gaps and risks plainly.
- Match depth to the audience and the clock — a two-line spot report and a full target package are different products.
- **Make finished reports readable and traceable.** Expand every reader-visible acronym or initialism at first authored use — including a heading, summary, caption or table cell — as `Full term (ACRONYM)`. Explain it in the report's language; retain an official or source-language full form where translation would obscure identity, then add a plain-language explanation. Never invent an expansion: mark it unestablished or ambiguous and carry that status into the glossary. Quotes, code, URLs, paths and literal identifiers remain byte-for-byte evidence; explain necessary terms beside them rather than rewriting those literals. A clickable link is not such evidence: use only a canonical, safe source locator in `href`, never an observed or target URL, a signed URL, or a URL carrying credentials, user-info, query data or fragments; describe unsafe URLs as inert, sanitised issuer-and-path locators instead.
- **Give every finished report an acronym chapter.** Title it `Acronyms and abbreviations`, translated to the report language (`Сокращения и аббревиатуры` in Russian), after the substantive findings and hand-off and before any source annex unless a specialist layout fixes its insertion point. Use `Acronym | Full form | Meaning in this report`; list every term actually used, once per meaning, including terms in headings and tables; alphabetise it; and keep explanations short. Exclude incidental uppercase machine literals. An ambiguous acronym receives qualified meanings, never a guess. With no terms, retain the chapter and say `None used.` A bounded status or dispatch hand-back is not a finished report and needs no artificial chapter, but it still expands reader-facing terms and references its evidence.
- **Use tables when comparison is the work.** Prefer labelled tables for systems, options or findings that share attributes, and for inventories, coverage and acronym definitions. Keep judgement, causal reasoning and the requested action in prose when that is clearer. Do not turn one straightforward finding into a table, and preserve a specialist layout's required tables rather than redesigning them.
- **Reference evidence where the claim is made.** Give each evidence-backed claim a canonical safe source locator, a document or artefact path relative to an identified evidence root or supplied bundle with page, section, line or offset where available, or an issuer-qualified document, entity, case or record locator. A source URL is clickable only when its canonical public locator has no credentials, user-info, query data or fragment and does not touch a target; otherwise render an inert, sanitised issuer-and-path locator. A numbered citation is enough only when it resolves to a complete locator elsewhere in the same report; an unconnected bibliography is not. A paragraph or table row may share one reference only when its support is unambiguous. Label inferences and cite their supporting observations. Quotations are optional, but check the supporting passage as well as the locator. If the source or precise anchor is unavailable, name that limitation rather than inventing a link or precise reference.
- **Make known evidence stores navigable.** When a canonical safe locator for the issuing evidence system is already known, use it in the claim-local reference rather than leaving a resolvable identifier inert. For Aleph, preserve the collection ID, exact entity ID and any needed offset in a link-ready receipt, then follow `aleph-entity-graph` for the authorised UI origin, entity route and coverage check. Where a safe locator is unavailable, say that the link is unavailable and retain the issuer-qualified locator; never manufacture one from collected material.
- State what you need from the reader: a decision, a resource, or an acknowledgement, with the deadline.
- **Give the task its own directory, under `.acordia/work/`.** Where a dispatch names no working directory, create one there and say where it is — not loose in the workspace you were pointed at. `.acordia/` is a hidden directory inside that workspace, and everything you generate goes under it. The workspace itself is where the corpus lives, so a file written loose beside the evidence joins the material you were asked to analyse, and the next pass over that corpus reads your own working as though someone had collected it. The directory holds a `README.md` carrying the request **verbatim**, its date, and one line on what is being settled — a record made at the time rather than reconstructed afterwards, so that a later reader has what the work was answering and not only what it concluded — and it holds your notes, your drafts and, where the work produces one, the credential file `credential-harvest-triage` governs.
- **Name it for the corpus, then the date.** The directory is `<corpus>-<YYYY-MM-DD>-<task-slug>`, and the product written from it takes that same stem under `.acordia/reports/`, so each is found from the other by name and neither needs a path recorded anywhere. That pairing is what the stem buys you, so where a brief names the directory instead, use the name as given and record where the product went — the stem is no longer carrying it for you. A date is not an identifier: two corpora swept on one day resolve to one name, and the second write **succeeds** — no harness reports it, and the loss surfaces only when a reader opens the report and finds the wrong corpus inside. The **corpus** token comes from the material rather than from the request: an Aleph collection's `foreign_id`, or a slug of its label where the instance supplies none, and for a file corpus a slug of the directory or archive you were handed. Derive it that way round, because a token taken from the request text splits one corpus across two directories the moment two dispatches word the same work differently. Where the material yields only a poor token — an opaque id, a truncated label — use it and say what you used and why: a degraded token still discriminates and a bare date does not. Where it yields nothing at all, say so and ask for a token rather than inventing one or falling back to the bare date this rule exists to replace. Where the stem is already taken, suffix it `-2`, `-3`, the directory and its product together; where one task produces two products, each carries the stem plus what it is. Where you cannot see what is already taken, because a sandbox does not show you the parent, say so rather than assuming the name is free. All of this is convention, as `.acordia/` itself is: nothing enforces a path here.
- **A task directory is shared, so each assignment owns its files.** The lead assigns every parallel leg instance a unique brief slug. With one supplied, write `notes-<your agent name>-<brief slug>.md` and, where needed, `credentials-<your agent name>-<brief slug>.md`; name both in your hand-back. With none, use `notes-<your agent name>.md` and `credentials-<your agent name>.md`, and say so in the hand-back. Two concurrent writes to one name are ordinary, not unlucky: the second succeeds, the first working is gone, and the lead can fuse one survivor believing it has both; a shared credential file also disconnects values from their classifications.
- **Name an Aleph evidence receipt as shared work.** An Aleph-backed report that cites entities keeps `evidence-links-<your agent name>-<brief slug>.md` beside its notes when the lead supplies a brief slug, or `evidence-links-<your agent name>.md` otherwise. The receipt is the expected set for the rendered-report coverage check, so two parallel legs must not share it; name it in the hand-back with the other working files.
- **Render with a parser, never a regex.** When the product must also exist in a second format — HTML, PDF, a deck — convert the source with a real parser for that format rather than a hand-written line-prefix pass. Inline emphasis, code spans, tables and inline links are exactly what a regex converter drops, and it drops them without erroring. Probe for an available parser, and say which one you used. Render only your own prose as markup: turn the parser's raw-HTML passthrough off and escape any markup inside quoted evidence, because the product carries verbatim material from the corpus and a real parser will render what a regex pass left inert — into the browser of the person you are briefing.
- **Cite identifiers in full.** A shortened hash or a truncated id reads as a citation and cannot be looked up. Carry the whole identifier into the product however long it is, and let the rendering shorten what is *displayed* rather than what is recorded. This governs identifiers that exist to be resolved — an entity or document id, a content hash, a case or ticket reference. A **target-owned** credential, and a corporate third-party one, are carried whole for that same reason — the recipient owns what it protects and cannot remediate from a classification — but a credential is never a *resolvable* identifier: resolving one against the system that issued it is a login attempt, so it is never part of the verification sample below, and `credential-harvest-triage` forbids trying one outright. What is never carried at all is a credential you own — your tooling, your C2 authentication, your staging accounts — at any length, along with any finding whose ownership you have not settled, because a product leaves your control when you hand it over. A personal identifier, including a third party's personal credential, is carried only as far as the judgement requires. Ownership is settled per `credential-harvest-triage`, and it is settled before the product is drafted rather than while it is being read.

## Signals / outputs

- A bottom-line-up-front judgement and recommendation.
- Confidence, key assumptions, and gaps flagged inline.
- An explicit ask: the decision or action required, by when.
- When the product is written to disk it lands in `.acordia/reports/` under its task directory's stem, the convention every analyst follows; returning it in-message instead is equally correct when the caller only needs the judgement — but only for a product carrying no credential values. One that carries them is always written, never returned: a reply is a message, and a value crosses only as a file its reader opens.
- A rendered product verified twice over: no source-format tokens survive in the output, and a sample of its evidence references has been resolved against the system that issued them — the instance, casefile or store you already read from, using the same read call that produced the reference. Resolve nothing else: not a URL that appears inside the material you are citing, and nothing target-owned or third-party, which would turn writing the report into an active touch. A reference that renders is not a reference that works — a truncated identifier produces a well-formed link to nothing, and counting links detects neither failure. Where the product carries credential values, verify it with a check that reports a verdict rather than content — a match count, an exit status — and reserve the draft for the questions a draft can answer. Whether the markup survived the render is precisely the one it cannot, so that is the question the check exists for: reading the rendered file back to see for yourself puts every value it carries into the session record, undoing at the last step what the handling rules held all the way through.
- **Reader check.** Before hand-over, inspect the actual finished product: every first visible term is expanded or explicitly unestablished, the acronym chapter is complete, each table makes a real comparison clearer, and every evidence-backed claim maps to the source that supports it. This is analyst judgement over the product, not a universal acronym-detector script; the rendered-product sample-resolution check above remains an additional obligation.
