# Add a native-root install route for omp

## Why

The marketplace route is sound and this change does not repair it. Verified 2026-08-21 against the 5.0.0 tree, in an isolated `--profile` whose effective `disabledProviders` was `[]`: `omp plugin marketplace add sapran/acordia-agents` followed by `omp plugin install acordia-analysts@acordia` produced a dispatchable pillar — `collection-analyst` ran, and its subagent transcript's `session_init` system prompt carried the six skill slugs unique to that agent's prompt. On a stock configuration, installing from the catalog works exactly as the distribution has always claimed.

What breaks is what happens when one discovery provider is switched off. omp serves a marketplace plugin's `agents/` directory only while the `claude-plugins` provider is enabled — `omp://task-agent-discovery.md` documents it as discovery input 4 — and marketplace skills and command wrappers arrive through that same provider. Enabling it is not a neutral act: `claude-plugins` reads both `~/.omp/plugins/installed_plugins.json` **and** `~/.claude/plugins/installed_plugins.json`, so it also surfaces every plugin registered in Claude Code's own registry, 19 of them on the author's machine. Turning it off to keep that ecosystem out of an omp session is a reasonable choice. And `claude-plugins` and `claude` are distinct ids inside the one shared `disabledProviders` namespace, so a user who disabled `claude` — Claude Code's context files, commands, skills and MCP — has not disabled marketplace plugins, and a user who disabled `claude-plugins` did so on purpose.

For that user the install is **completely inert while every stored signal reports health.** `omp plugin list` shows the plugin. `~/.omp/plugins/installed_plugins.json` records it. `~/.omp/plugins/omp-plugins.lock.json` says `"enabled": true`. `~/.omp/plugins/node_modules/acordia-analysts` symlinks into the cache. There is no error and no warning at any point, and the only command that reveals the cause is `omp config get disabledProviders`, which reports the merged effective value. A user in this state has five agents and 45 skills installed and none of them exist.

No packaging change can fix it, and this was measured rather than assumed. With `claude-plugins` disabled, every non-marketplace surface the omp documentation claims serves agents fails to, except one: a user `extensions:` entry in `config.yml` pointing at a bare directory loads the skills and drops the agents; the same directory carrying a `package.json` behaves identically; and a properly registered `omp plugin link` npm plugin — shown by `omp plugin list` as `npm Plugins: ● acordia-analysts@5.0.0`, `enabled: true` in the lockfile, symlinked into `~/.omp/plugins/node_modules/` — also loads the skills and drops the agents. Only the CLI flag `omp -e <absolute path>` serves agents from such a root. This contradicts discovery input 3 of `omp://task-agent-discovery.md`, which lists project and user `extensions:` settings and installed npm/link plugins in the same tier as CLI `--extension`. It is an omp bug rather than a packaging error, which is exactly why adding a `package.json` to the pillar buys nothing.

The two roots that are gated by no discovery provider at all are omp's native ones: the nearest project `.omp/agents` and the user agent directory's `agents/`, discovery inputs 1 and 2. A skill directory reached by symlink in the native skills root resolves correctly — verified by a `skill://` read whose resolved path in the session log was `profiles/insttest/agent/skills/take-domain-interpretation`, that is, through the symlink. Writing into those roots is therefore the one route that cannot be silenced by a provider setting, and it is what this change adds.

## What changes

- **Two scripts under `tools/`** — `tools/install-omp.sh` and `tools/uninstall-omp.sh`, both executable bash under `set -euo pipefail`. They are an alternative route into omp for the gated case, not a replacement for the marketplace.
- **Install symlinks, it does not copy.** Each of the five `acordia-analysts/agents/*.md` is linked into `<agent-dir>/agents/` and each of the 45 `acordia-analysts/skills/*/` directories into `<agent-dir>/skills/`. Because they are symlinks, a `git pull` changes what omp serves without a reinstall.
- **One shared interface**, `[--profile <name>] [--agent-dir <path>] [--dry-run]` plus `-h/--help`, with `--profile` and `--agent-dir` mutually exclusive. Target-directory precedence is `--agent-dir`, then `--profile` resolving to `~/.omp/profiles/<name>/agent`, then `$PI_CODING_AGENT_DIR`, then `~/.omp/agent`.
- **No configuration file is edited.** Neither script writes `config.yml`, a profile, a plugin registry or a lockfile. The only filesystem changes are inside the two roots.
- **A collision preflight aborts the whole run.** Any target that already exists and is not one of our own symlinks — a symlink whose `readlink` target lies inside this checkout's pillar — stops the run, prints every colliding path, and changes nothing at all. Verified: a single planted real `cyber-analyst.md` aborted the run and left all 45 skills unlinked. A re-run over an install we already made is idempotent.
- **Uninstall matches on the recorded target, not on the checkout.** It removes only symlinks whose `readlink` target contains `/acordia-analysts/agents/` or `/acordia-analysts/skills/`, so a real file is never deleted and neither is a symlink pointing elsewhere, and links whose checkout has since been deleted, renamed or moved are still cleaned — a dangling symlink is still readable. It removes the two roots only when it emptied them itself. Verified: with 50 ACORDIA links plus a planted real `mine.md` and a planted foreign symlink `decoy`, it reported `Removed 50 ACORDIA links` and `Left 2 entries that are not ours`, and both planted entries survived.
- **Command wrappers are not installed by this route.** A wrapper takes its namespace from the plugin name and exists only through a plugin root, so this route cannot serve one and does not pretend to.
- **Version 5.0.0 → 6.0.0.** The shape of the distribution changes: it gains a second install route.

## Impact

- Affected specs: `plugin-distribution` — one requirement modified, because *A harness install SHALL therefore consist of resolving the catalog and copying the plugin directory* is no longer true as an exclusive claim, and one requirement added for the script route.
- Affected code: two new files under `tools/`. The distribution still has no runtime, no generator and no build step, and the scripts introduce no gate — nothing in a hook or a workflow invokes them.
- `openspec/config.yaml`'s project context states "There is no generator, no build step and no shell installer". The last clause of that sentence becomes false with this change, so it must be corrected in lockstep: the first two clauses still hold and the sentence must not be deleted wholesale.
- **In the wild:** omp's native roots dedup first-wins by exact agent name and resolve before plugin roots, so a user who runs the script while a marketplace install is live gets the native copy and no notice that the plugin one was shadowed. Both point at authored files, so the practical effect is limited to which of two checkouts wins; it is documented rather than guarded.
- **Verified end to end** in an isolated profile: install linked five agents and 45 skills, a dispatched `collection-analyst` returned its exact token with the five agent-unique slugs in its subagent prompt, and `skill://take-domain-interpretation` resolved through the symlink.
